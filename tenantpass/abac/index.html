ABAC — политики доступа

ABAC — политики доступа

Attribute-Based Access Control. Решение принимается по атрибутам трёх категорий:

КатегорияПримеры
Пользователь (subject)tenant_id, site_id, department, роль, метод аутентификации (amr)
Ресурсdoor:room-215, resource.tenant_id, resource.site_id, shift_end
Окружениевремя суток, IP-адрес, тип устройства

Пример политики

Политика: "tenant-manager-access"
  Role policy:       user has role "tenant_manager"
  AND
  Attribute policy:  user.tenant_id == resource.tenant_id
  AND
  Attribute policy:  user.site_id   == resource.site_id
  AND
  Time policy:       now within work_hours
  AND
  Auth policy:       amr contains "fido2" OR "nfc"

Важно: Organization scope — не access gate

Если пользователь не в организации, scope organization:<alias> молча отбрасывается, запрос не отклоняется. Нельзя полагаться на presence scope как на запрет.

Всегда проверять org claim в приложении, а не только в политике Keycloak.

Паттерн: RBAC + ABAC

Чистый ABAC без ролей быстро становится неподдерживаемым.

  • Роли задают класс доступа (менеджер, HR, аудитор)
  • Атрибуты сужают его до конкретного объекта / записи / времени

Задержка и автономность

Запрос к Keycloak — сетевой вызов. Для дверей/лифтов:

  • Локальный кэш решений на агенте (30–60 сек)
  • При недоступности Keycloak → режим по последним известным разрешениям
  • Мониторинг доступности; алерты при потере связи
