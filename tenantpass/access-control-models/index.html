DAC — Discretionary Access Control

Принцип: владелец ресурса сам решает кому дать доступ.

Пример: файловая система Linux
  owner: user1, group: staff, other: ---
  user1 может дать доступ user2 командой chmod

Плюсы: просто, гибко для владельца
Минусы:
  - Масштаб: 1000 дверей × 500 сотрудников = 500 000 решений
  - Нет централизованного контроля
  - Сложно аудировать «кто что разрешил»

*Применение в Pass: не используется как основная модель. Элементы DAC есть в HomePass — владелец сам управляет гостевыми доступами.

MAC — Mandatory Access Control

Принцип: система присваивает метки (labels) субъектам и объектам. Доступ — только если метка субъекта ≥ метки объекта.

Уровни: UNCLASSIFIED < CONFIDENTIAL < SECRET < TOP SECRET

Субъект: сотрудник с меткой SECRET
Объект:  дверь серверной с меткой SECRET
Решение: SECRET ≥ SECRET → разрешить

Объект:  дверь ЦОД с меткой TOP SECRET
Решение: SECRET < TOP SECRET → запретить

*Применение в Pass: MAC-принципы применяются в TenantPass для зон с повышенным контролем:

# Зоны с MAC-уровнями
zones:
  lobby:         clearance_level: 0   # любой
  open_office:   clearance_level: 1   # сотрудник
  management:    clearance_level: 2   # менеджмент + выше
  server_room:   clearance_level: 3   # IT + безопасность
  treasury:      clearance_level: 4   # финансовый директор + аудитор

# Правило: user.clearance_level >= zone.clearance_level
# Принцип Bell-LaPadula: no read up, no write down

RBAC — Role-Based Access Control

Принцип: пользователь → роль → права. Права назначаются роли, а не человеку.

Иерархия RBAC:
  User → Role → Permission → Resource

  Иванов → employee → read(timesheet:own)
  Петров → site_manager → read(timesheet:site), write(timesheet:site)
  Сидоров → admin → all(*)

Иерархия ролей в TenantPass:

graph TD SUPERADMIN["superadmin\n(платформа)"] TENANT_ADMIN["tenant_admin\n(арендатор)"] SITE_MANAGER["site_manager\n(объект)"] HR["hr\n(кадры)"] SECURITY["security\n(охрана)"] EMPLOYEE["employee\n(сотрудник)"] CONTRACTOR["contractor\n(подрядчик)"] VISITOR["visitor\n(посетитель)"] AUDITOR["auditor\n(аудитор)"] SUPERADMIN --> TENANT_ADMIN --> SITE_MANAGER SITE_MANAGER --> HR & SECURITY & EMPLOYEE EMPLOYEE --> CONTRACTOR --> VISITOR TENANT_ADMIN --> AUDITOR

Плюсы RBAC: просто, понятно, легко аудировать.
Минусы: «роль взрывается» при росте числа ресурсов и условий (role explosion).

Проблема: 
  employee_floor1_morning
  employee_floor1_evening
  employee_floor2_morning
  employee_floor2_evening
  contractor_floor1_morning
  ... → 100+ ролей для одного объекта

ABAC — Attribute-Based Access Control

Принцип: решение = f(атрибуты субъекта, атрибуты ресурса, контекст среды).

# Решение access control как функция
def can_access(subject: dict, resource: dict, environment: dict) -> bool:
    return (
        subject["tenant_id"] == resource["tenant_id"]      # тот же арендатор
        and subject["clearance"] >= resource["min_clearance"]
        and resource["zone_id"] in subject["permitted_zones"]
        and environment["hour"] in resource["allowed_hours"]
        and environment["auth_method"] in resource["required_amr"]
    )

*Атрибуты в платформе Pass:

КатегорияАтрибуты
Субъектuser_id, tenant_id, site_id, department, employment_type, clearance_level, amr (как аутентифицирован), device_trusted
Ресурсresource_type (door/zone/report), tenant_id, site_id, zone_id, risk_level, required_amr, allowed_hours
Средаcurrent_time, day_of_week, network_zone, ml_risk_score, fire_alarm_active

XACML Policy (стандарт OASIS) — концептуально:

<Policy PolicyId="employee-door-access">
  <Target>
    <AnyOf>
      <AllOf>
        <Match MatchId="string-equal">
          <AttributeValue>door</AttributeValue>
          <AttributeDesignator Category="resource" AttributeId="resource-type"/>
        </Match>
      </AllOf>
    </AnyOf>
  </Target>
  <Rule Effect="Permit">
    <Condition>
      <!-- субъект в той же организации что ресурс -->
      <Apply FunctionId="string-equal">
        <AttributeDesignator Category="subject" AttributeId="tenant_id"/>
        <AttributeDesignator Category="resource" AttributeId="tenant_id"/>
      </Apply>
      <!-- рабочее время -->
      <Apply FunctionId="time-in-range">
        <AttributeDesignator Category="environment" AttributeId="current-time"/>
        <AttributeValue>08:00:00</AttributeValue>
        <AttributeValue>20:00:00</AttributeValue>
      </Apply>
    </Condition>
  </Rule>
</Policy>

Keycloak Authorization Services реализует ABAC через:

  • UMA 2.0 — User Managed Authorization
  • Resource Scopes — ресурсы и разрешения
  • Policy Evaluation — REST endpoint для PEP

ReBAC — Relationship-Based Access Control

Принцип: доступ определяется отношениями в графе (Google Zanzibar, 2019).

Граф отношений:
  User:Alice --[owner]--> Document:report_q4
  User:Bob   --[viewer]--> Document:report_q4
  Group:marketing --[member]--> User:Alice
  Folder:finance --[contains]--> Document:report_q4
  User:Bob --[member]--> Group:finance_team
  Group:finance_team --[viewer]--> Folder:finance

Вопрос: может ли Bob смотреть report_q4?
Ответ:  Bob → member → finance_team → viewer → Folder:finance
        → Folder:finance contains Document:report_q4 → YES

Реализации: Google Zanzibar, OpenFGA (CNCF), SpiceDB, Warrant.

Применение в TenantPass: для иерархии зон и делегирования.

# OpenFGA schema для TenantPass
type user

type organization
  relations
    define admin: [user]
    define member: [user] or admin

type site
  relations
    define organization: [organization]
    define manager: [user] or admin from organization
    define employee: [user] or manager

type zone
  relations
    define site: [site]
    define can_enter: employee from site or manager from site
    define can_manage: manager from site

type door
  relations
    define zone: [zone]
    define can_open: can_enter from zone

# Проверка: может ли user:alice открыть door:server_room_1?
fga_client.check({
    "user": "user:alice",
    "relation": "can_open",
    "object": "door:server_room_1"
})
# → True/False за ~5 мс (граф в памяти)

PBAC — Policy-Based Access Control

Принцип: политики написаны как код (Policy as Code). OPA (Open Policy Agent) + Rego язык.

# opa/policies/door_access.rego
package tenantpass.access

import future.keywords.if
import future.keywords.in

# Разрешить вход если:
allow if {
    input.resource.type == "door"
    input.subject.tenant_id == input.resource.tenant_id
    input.subject.clearance_level >= input.resource.min_clearance
    current_hour := time.clock(time.now_ns())[0]
    current_hour >= 8
    current_hour < 20
    input.subject.auth_method in {"fido2", "nfc", "ble_beacon"}
    input.environment.ml_risk_score < 0.5    # ← ML интеграция
    not input.environment.fire_alarm_active  # ← IoT интеграция
}

# Экстренный режим: при пожаре — все двери открыты
allow if {
    input.resource.type == "door"
    input.resource.fail_mode == "fail_open"
    input.environment.fire_alarm_active
}

# Интеграция OPA с PEP агентом
import httpx

async def check_policy_opa(subject: dict, resource: dict, env: dict) -> bool:
    async with httpx.AsyncClient() as c:
        r = await c.post("http://opa:8181/v1/data/tenantpass/access/allow",
                         json={"input": {
                             "subject": subject,
                             "resource": resource,
                             "environment": env
                         }})
    return r.json()["result"]

Zero Trust

Принцип: не доверяй никому по умолчанию. Верифицируй каждый запрос, каждый раз.

Традиционная модель (замок-ров):
  Внутри сети → доверяем → доступ ко всему
  
Zero Trust:
  Даже внутри сети → каждый запрос требует аутентификации + авторизации
  Каждый сотрудник → минимум привилегий
  Каждое устройство → проверяется (MDM, сертификат)
  Каждый доступ → логируется и анализируется ML

Zero Trust в TenantPass:

1. Идентификация: каждый запрос несёт токен (JWT) — нет анонимных
2. Контекст: ML risk score включён в решение
3. Минимум привилегий: RBAC + ABAC ограничивают до конкретного объекта
4. Непрерывная верификация: Continuous Authentication (BLE поведение)
5. Микросегментация: каждый сервис в отдельном VLAN/namespace
6. Шифрование: mTLS между сервисами (Istio/Envoy)

Что выбрано для платформы *Pass

ПроектОсновная модельДополнения
TenantPassRBAC + ABAC (Keycloak)MAC для зон, OPA для сложных политик, ReBAC для иерархии
HomePassRBAC (простое)DAC для гостевых доступов
EventPassABAC (атрибуты билета)ReBAC для вложенных зон мероприятия

Почему не чистый ReBAC: требует отдельного граф-сервиса (OpenFGA/SpiceDB), сложность операции. Оправдано при 100+ типах ресурсов и глубокой иерархии.

Почему не чистый OPA: Keycloak Authorization Services даёт 80% ABAC без дополнительного сервиса. OPA подключается опционально для сложных случаев.
