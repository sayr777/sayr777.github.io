API между агентами и Keycloak

API между агентами и Keycloak

Паттерн PEP / PDP

sequenceDiagram participant T as Терминал/считыватель participant A as Агент-контроллер (PEP) participant K as Keycloak (PDP) participant D as Физическое устройство T->>A: 1. идентификация пользователя A->>K: 2. запрос решения (uma-ticket) K-->>A: 3. permit / deny A->>D: 4. исполнение — открыть замок / заблокировать

Агент никогда не принимает решение самостоятельно. Он только запрашивает и исполняет.

Endpoint’ы Keycloak, которые использует система

1. Token endpoint — получить токен пользователя

POST /realms/{realm}/protocol/openid-connect/token

Используется: мобильное приложение / веб-UI при логине.

Flows:

  • Authorization Code + PKCE — для браузера/приложения (рекомендуется)
  • Device Authorization Grant — для терминалов без браузера
  • Token Exchange — агент обменивает внешнее подтверждение (NFC/BLE) на токен Keycloak

2. Entitlement API — запрос разрешений на ресурс

POST /realms/{realm}/protocol/openid-connect/token

Body:
  grant_type=urn:ietf:params:oauth:grant-type:uma-ticket
  audience={resource_server_client_id}
  permission={resource}#{scope}
  subject_token={user_access_token}

Возвращает RPT (Requesting Party Token) — токен с вложенными разрешениями.

Агент двери использует именно этот endpoint: «пользователь X хочет scope enter на ресурс door:room-215».

// Тело ответа при permit
{
  "access_token": "<RPT>",
  "authorization": {
    "permissions": [
      {
        "rsid": "door-room-215",
        "rsname": "door:room-215",
        "scopes": ["enter"]
      }
    ]
  }
}

При deny — 403 Forbidden с error: access_denied.

3. Token Introspection — проверить валидность токена

POST /realms/{realm}/protocol/openid-connect/token/introspect

Body:
  token={RPT}
  token_type_hint=requesting_party_token

Агент может локально кэшировать RPT и периодически проверять через introspection вместо нового запроса. Полезно для уменьшения нагрузки при повторных проходах.

4. Resource Registration API — регистрация ресурсов

POST /realms/{realm}/authz/protection/resource_set

Body:
{
  "name": "door:room-215",
  "type": "physical-access:door",
  "resource_scopes": ["enter", "exit"],
  "attributes": {
    "site_id": "building-A",
    "tenant_id": "tenant-xyz",
    "floor": "3"
  }
}

Каждая дверь, лифт, рабочая станция регистрируется как ресурс с атрибутами. Именно по этим атрибутам Keycloak оценивает ABAC-политики.

5. Admin REST API — управление пользователями и организациями

# Создать пользователя
POST /admin/realms/{realm}/users

# Добавить в организацию
POST /admin/realms/{realm}/organizations/{org-id}/members

# Назначить атрибуты
PUT /admin/realms/{realm}/users/{user-id}
Body: { "attributes": { "site_id": ["building-A"], "tenant_id": ["tenant-xyz"] } }

Используется: сервис управления (onboarding сотрудников, смена объекта).

Admin API — только из защищённого управляющего сегмента сети. Никогда не из пользовательского контура.

Сценарий: агент двери открывает замок

1. Считыватель определяет пользователя (BLE RSSI / NFC tap / passkey)
   └─► идентификатор устройства + user_token (из приложения или локального кэша)

2. Агент-контроллер:
   POST /realms/tenantpass/protocol/openid-connect/token
     grant_type=uma-ticket
     audience=door-controller-client
     permission=door:room-215#enter
     subject_token=<user_access_token>

3. Keycloak оценивает политики:
   - user.role == "employee" ✓
   - user.site_id == door.site_id ✓
   - time.in(work_hours) ✓
   - amr contains "fido2" ✓
   → permit

4. Агент получает RPT → замыкает реле → дверь открывается

5. Агент пишет событие в журнал:
   { user_id, door_id, timestamp, decision: "permit", amr: "fido2" }

Сценарий: агент ПК разблокирует сессию

Два варианта:

A. Kerberos / SPNEGO (если домен)

ПК → браузер/агент передаёт Negotiate-токен → Keycloak валидирует → SSO

B. Агент с запросом к Keycloak

Агент на ПК (при приближении пользователя по BLE):
  1. Получает user_token из корпоративного приложения
  2. POST uma-ticket для ресурса workstation:pc-42 scope:unlock
  3. При permit → разблокирует сессию ОС

Кэширование решений на агенте

Сетевой вызов к Keycloak занимает 20–100 мс. Для двери это заметно.

Стратегия:

if cached_decision.valid and cached_decision.age < 45s:
    use cached_decision          # не ходим в Keycloak
else:
    fetch new RPT from Keycloak  # обновляем кэш
    cached_decision = new RPT

# При отзыве доступа (увольнение):
# Keycloak ставит not-before → следующий запрос получит 403
# Максимальная задержка = TTL кэша (45 сек)

Важно: из-за CVE-2026-18218 (not-before policy может молча игнорироваться) — при критичных отзывах (увольнение, инцидент) агент должен принудительно сбросить кэш и запросить свежее решение.

Режим автономности (Keycloak недоступен)

if keycloak.unreachable:
    last_known = load_from_local_cache()   # последние известные разрешения
    if last_known.age < MAX_OFFLINE_TTL:   # например, 4 часа
        use last_known                     # ограниченный доступ
    else:
        deny_all_except_emergency_list     # только экстренный список
    log_offline_event(user, door, reason)

При восстановлении связи — принудительная синхронизация.
