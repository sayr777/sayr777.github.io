Keycloak — архитектурные решения

Keycloak — архитектурные решения

Роль в системе

Keycloak — не средство защиты информации и не «коробка». Это движок политик и центр идентичности.

Декларировать: «компонент аутентификации и авторизации на базе open-source Keycloak, интегрированный в продукт. Keycloak не предоставляет UI. Средства защиты — отдельные сертифицированные компоненты.»

Мультикластерная репликация (Multi-cluster v2)

Рекомендуемый подход (не требует внешнего Infinispan):

  • Несколько независимых кластеров Keycloak → одна синхронно реплицируемая БД
  • Кэши локальные, инвалидация через БД (outbox)
  • Требование: commit latency < 5 мс (макс. 10 мс) между сайтами
  • Обновления realm замедляются на ~100 мс — не критично

Уязвимости и риски

  • CVE-2026-9791 — при отключении Organizations Account API продолжает возвращать org-данные → downstream-сервисы могут применять авторизацию по org, хотя она «выключена»
  • CVE-2026-18218 — отзыв токенов через not-before policy молча игнорируется при наличии старой non-zero политики. Уволенный сотрудник может сохранить доступ к двери!
  • Organization invite race condition (26.6.2) — ссылку-приглашение можно открыть одновременно два раза

Что Keycloak не умеет (и где нужны агенты)

  • Не открывает двери физически — нужен локальный контроллер
  • Не читает NFC/BLE — сигнал передаёт сенсорный слой
  • Не хранит биометрические шаблоны — passkeys хранят приватный ключ на устройстве
  • Не считает переработки — нужен отдельный сервис учёта времени

Hardening

  • Отключить стандартный UI (login, account, admin консоль) из пользовательского контура
  • Admin API — только из защищённого сегмента
  • Контейнер: --cap-drop=ALL, --read-only, non-root user
  • Изолировать IPMI/BMC в отдельный management VLAN
