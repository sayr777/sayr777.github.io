Мультиарендаторность: Organizations vs Realms

Мультиарендаторность: Organizations vs Realms

Два пути

Organizations внутри одного Realm

Когда выбирать: арендаторов десятки, не нужна полная изоляция политик аутентификации.

Плюсы:

  • Создание за 0.03 сек vs 0.53 сек для realm
  • Единая точка администрирования
  • Пользователь может быть в нескольких организациях одновременно
  • Автоматическая маршрутизация по домену email (@tenant-a.com)
  • Fine-Grained Admin Permissions с 26.7 (администратор видит только свою org)

Ограничения (критические):

  • Organization Groups нельзя использовать в Authorization Policies — только realm-группы
  • Нет per-organization политик аутентификации (MFA, пароли, время жизни токенов)
  • Нет per-organization темы логина
  • Производительность: при 300+ org + persistent user sessions → падение после 300 RPS. Решение: отключить persistent sessions → масштаб до 5000 org
  • Баг (issue #48654): count() при проверке существования org при миллионах org = spike CPU на БД

Отдельные Realms

Когда выбирать: нужна полная изоляция ключей/политик, арендаторов < 50.

Плюсы:

  • Свои ключи подписи, политики, MFA, темы, token lifespans
  • Полная изоляция производительности

Потолок: ~500 realm на узел — после этого десятки ГБ памяти и Admin API перестаёт отвечать.

Гибрид (рекомендация)

Большинство арендаторов → Organizations. Несколько крупных / регулируемых → отдельные realms.

Изоляция данных — ваша ответственность

Organizations дают логическую изоляцию идентичности, а не данных. Сервис учёта времени и БД должны самостоятельно обеспечивать row-level security или отдельные схемы по tenant_id.

Keycloak кладёт org claim в токен — дальше каждый сервис обязан его проверять.
